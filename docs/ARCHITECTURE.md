# معماری آبرنگ — چه چیزی کجاست و چرا؟

ایدهٔ اصلی یک جمله است: **«سایت به‌مثابه کد» (Site as Code)** —
هر چیزی که برای ساختِ دوبارهٔ سایت لازم است، به‌صورت فایل متنی داخل گیت است؛
هر چیزی که «اطلاعاتِ زنده» است (محصولات، سفارش‌ها، عکس‌های آپلودشده، رمزها) بیرون گیت نگه داشته می‌شود.

```
  Browser ── http://localhost:8080 ──► ┌────────────────────┐
                                        │ wordpress container │──►┌─────────────┐
                                        │  Apache + PHP 8.3   │   │ db container │
                                        └───────▲────────────┘   │  MariaDB 11  │
                                                │                └──────▲──────┘
            This repo (git)                     │ bind mount            │
            wp-content/themes/abrang ───────────┘ (theme, live)         │
                                                                        │
            scripts/setup.sh ──► ┌────────────────────┐                 │
                                 │  wpcli container    │── WP-CLI ──────┘
                                 │  (runs on demand)   │
                                 └─────────────────────┘
            Named Docker volumes: wp_data (WordPress core + plugins + uploads)
                                  db_data (the whole database)
```

## چه چیزی کجاست؟

| کجا | چه چیزهایی | چرا آنجاست؟ |
|---|---|---|
| **گیت (این مخزن)** | `docker-compose.yml`، اسکریپت `scripts/setup.sh`، قالب `wp-content/themes/abrang` (شامل فونت وزیرمتن)، تست خودکار CI، فایل نمونه `.env.example` | اینها «دستور پخت» سایت‌اند: کوچک، قابل بازبینی در Pull Request، قابل برگشت به نسخه قبل. هر کس با `git clone` دقیقاً همین سایت را می‌سازد. |
| **والیوم `wp_data`** (داخل Docker) | فایل‌های هستهٔ وردپرس، افزونه‌های دانلودشده از wordpress.org (ووکامرس و ووکامرس فارسی)، `wp-config.php`، فایل‌های آپلودشده (`uploads`) | هزاران فایل آمده از بیرون‌اند و هر لحظه قابل دانلود دوباره‌اند؛ آوردنشان به گیت فقط مخزن را سنگین و بازبینی را ناممکن می‌کند. آپلودها دادهٔ زنده‌اند و جای بکاپشان جای دیگری است (قدم انتشار). |
| **والیوم `db_data`** (داخل Docker) | کل دیتابیس: نوشته‌ها و برگه‌ها، محصولات و سفارش‌ها در آینده، کاربران، و تنظیمات ذخیره‌شدهٔ وردپرس | دیتابیس با هر کلیک در پیشخوان عوض می‌شود؛ فایل دیتابیس در گیت یعنی هر تغییر کوچک، یک کامیت غول‌پیکر و غیرقابل‌ادغام. |
| **فایل `.env`** (فقط روی کامپیوتر شما) | رمز دیتابیس و ادمین، آدرس و پورت سایت | رمز واقعی هیچ‌وقت نباید به گیت‌هاب برود. در مخزن فقط `.env.example` با مقدارهای نمونه هست و `.gitignore` مانع کامیت اشتباهی `.env` می‌شود. |

## `setup.sh` مغز این معماری است

تنظیمات پایهٔ سایت (زبان فارسی، منطقه زمانی تهران، پیوند یکتا، واحد تومان، فعال بودن قالب و…) در دیتابیس زندگی می‌کنند —
اما «منبع حقیقت»شان اسکریپت `scripts/setup.sh` است که آنها را با WP-CLI تنظیم می‌کند.
اسکریپت **Idempotent** است: هر قدم اول وضعیت فعلی را چک می‌کند و فقط اگر لازم بود کاری می‌کند؛ پس ده بار اجرایش با یک بارش فرقی ندارد.
نتیجه‌اش این است که دیتابیس را می‌شود هر وقت لازم شد دور انداخت و در چند دقیقه، سایتِ تنظیم‌شده را از روی کد دوباره ساخت
(`docker compose down -v` ← `up -d` ← اجرای اسکریپت).

## چرا این نظم به نفع ماست؟

- **قابل بازسازی و قابل اثبات:** تست خودکار CI در هر تغییر، کل سایت را روی سرور گیت‌هاب از صفر می‌سازد، اسکریپت را دو بار اجرا می‌کند و فارسی/راست‌چین بودن، فعال بودن قالب آبرنگ و تومان بودن واحد پول را بررسی می‌کند. سبز بودن CI یعنی «کلون تازه = سایت سالم».
- **امن:** رمز و اطلاعات مشتری هرگز وارد تاریخچهٔ گیت نمی‌شود.
- **تغییر قالب فوری:** پوشهٔ قالب از مخزن مستقیم داخل کانتینر وصل است (bind mount)؛ ویرایش فایل قالب = تغییر فوری در سایت، بدون ساخت دوباره ایمیج.
- **مستقل از CDN:** فونت وزیرمتن داخل قالب و روی خود سرور است (برای بازدیدکننده ایرانی سریع و قابل اتکا)، نه روی Google Fonts.

## چه چیزی عمداً هنوز نیست؟ (قدم‌های بعدی)

طراحی ظاهری و صفحه خانه، محصولات و دسته‌بندی‌ها، درگاه پرداخت ایرانی، روش‌های ارسال، سئو، و انتشار روی abrang.com
(جایی که بکاپ دیتابیس و آپلودها و رمزهای واقعی تولید هم تعریف می‌شوند).
